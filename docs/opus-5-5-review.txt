  高危（会静默写坏数据）

  1. USB→I2C 寄存器面板：按页写 EEPROM 时数据会写花
  - 位置：app/i2c/protocol.js:387 planWrite()，调用方是 app/i2c/reg-view.js:184。
  - 原因：分片只按 chunkMax（8/32 B）切，没有按页边界对齐。面板推荐的用法是“写分片 8 B + 片间等 6 ms”，但只要起始地址不是 8 的倍数，或者改动的字节跨了页，就会有一片跨页，器件内部回绕到页首把数据盖掉。
  - 实测（假探针上的 AT24C02 模型，页内回绕和真片一致）：
  A 起始 0x05 整块写 16 B  期望 a0 a1 … af  回读 a0 a1 a2 ab ac ad ae af a8 a9 aa 00 … ✗
  B 只改 +6..+9            期望 …00 11 22 33 44 00…  回读 33 44 00 00 11 22 00 … ✗
  - 更糟的是写完后 reg-view.js:190 直接 base = cur，黄框消失，界面显示成功。
  - 修复：planWrite 加一个 pageSize 参数，切片时再限制 n ≤ pageSize - (地址 % pageSize)，地址按完整子地址算。面板的“写分片”选项改成“页大小”的含义。写 EEPROM 后建议自动回读校验。
  - 把握度：高（端到端复现）。现有测试 i2c-registers.test.mjs 段 D 只测了从 0x00 起、页对齐的情况，所以一直是绿的。

  2. SPI NOR“写测速”：只有第一个扇区真被擦掉
  - 位置：app/spi/bus-view.js:1132-1135 flWriteBench()。
  - 原因：先擦一次 addr，然后循环 off=0,4K,8K… 又从 addr+0 开始擦。每条擦除之间不轮询 BUSY。扇区擦除要几十到几百 ms，器件忙的时候会忽略后面的命令（文件里给页编程写的注释就说过这一点）。
  - 实测（用 FlashDevice 模型按同样的顺序发，间隔 2 ms）：
  SE 0x0 已执行；SE 0x0 / 0x1000 / 0x2000 / 0x3000 → 器件 BUSY，命令被忽略
  扇区 0x1000、0x2000、0x3000：✗ 没擦
  - 后果：在有旧数据的区域跑写测速，回读会不一致。日志会把原因引向“tPP 太短”，方向是错的。起始地址不按 4K 对齐时，最后一个扇区连命令都不会发。
  - 修复：去掉重复的那次擦除。每个 SE 之后调 flWaitReady()。循环按 sectorOf(addr) 到 sectorOf(addr+n-1) 走。
  - 把握度：高（命令序列和器件行为都读码核实过；模型模拟复现）。

  3. SPI Flash 地址输入非法时静默落到 0x000

    - 输入 abc、空串得到 0，4096.7 得到 4096，-1 得到 0xFFFFFFFF。
    - 帧里地址固定是 3 字节（flash.js 的 addrLen: 3），所以 ≥16 MB 的地址在线上会回绕。

  高危

  6. 目标日志里只要出现 “SEGGER RTT” 这串字，RTT 通道就会永久卡死
  - 位置：app/rtt/protocol.js:323-331 readUp()。
  - 原因：为了防“错位读”，代码把“数据里出现控制块签名 SEGGER RTT”当成读错了的标志。出现时整段丢掉，并且不推进 RdOff，下一轮重读。可如果这串字本来就是目标正常打印出来的（比如 printf("SEGGER RTT
    ready\n")），每次重读结果都一样。RdOff 永远不动，后面的日志一条都出不来。
  - 连锁影响：RTT Viewer 会把它当成链路故障。rtt/view.js:616-630 会先反复做 SWD 重激活、重开 USB，150 轮后报“SWD 链路不稳定，把时钟调低”，排查方向完全错。
  - 复现（rtt-sig.mjs，内存模拟的控制块）：
  第1轮 bytes=0 corrupt=true RdOff=0
  第2轮 bytes=0 corrupt=true RdOff=0
  第3轮 bytes=0 corrupt=true RdOff=0
  - 修复建议：不要只看内容。可以连读两次，两次结果完全相同就采信（真正的错位读几乎不会两次一模一样）；或者只有签名出现的位置刚好等于控制块地址的偏移时才判错位。
  - 把握度：高。

  7. Intel HEX 不检查校验和和长度，损坏的文件会被照常烧进去，而且回读校验也会通过
  - 位置：app/flash/image.js:85-110 parseIntelHex()。
  - 原因：每行末尾的校验字节完全没用到。长度字段 ll 也不和实际字节数比对，记录被截断时会把校验字节当成数据。
  - 复现（hex-checksum.mjs）：
  数据位翻错   → 接受 [01 02 03 05]   （正确应为 01 02 03 04）
  行被截断     → 接受 2B [01 f2]      （f2 是校验字节）
  - 后果：烧录后的校验比对的就是这份已经坏掉的数据，所以界面显示“校验通过”。
  - 修复：每行检查“所有字节之和 & 0xFF == 0”，并且要求 body.length/2 === len + 5，不符合就报错并带上行号。
  - 把握度：高。

  8. J-Scope 有两个返回码网页解释不了或解释错了

  9. DP 上电等待检查的应答位不对
  - 位置：app/rtt/dap-webusb.js:831,836。
  - 按 ADIv5，CTRL/STAT 的 bit31 是 CSYSPWRUPACK，bit29 是 CDBGPWRUPACK。代码用 st & 0x30000000 判断，实际查的是 bit29 加 bit28（bit28 是 CDBGPWRUPREQ，请求位）。结果是系统域还没上电就提前判成功。写入的值
    0x50000022/0x50000000 本身是对的。
  - 同一个文件里关于这几个位的注释有三处互相矛盾：
    - 第 29-37 行说 30/31 是请求位，“正确值 0xC0000000”，这是错的；
    - 第 757 行是对的；
    - 第 792-800 行又写成 bit29 是 CSYSPWRUPREQ。
  - 第 39 行的 DP_PWRUP = 0xc0000000 没人用，但数值是错的，以后有人拿来用会出事。
  - 修复：掩码改成 0xA0000000；删掉 DP_PWRUP；三段注释统一成 ADIv5 的定义。

  10. 跨页签让出探针的等待上限可能不够
  - 位置：app/core/probe-bus.js:146-148。
  - 请求方最多等 1.2 s，循环里用的是 sleep(40)。被要求让出的那个页签通常在后台，它在 onRelease 里断开 RTT/scope/HID/SPI/I2C 并关闭 USB。这条路径上有多处 sleep(120~250)（比如
    dap-webusb.js:1263,1298），后台每处都会被钳到 1 s，加起来很容易超过 1.2 s。
  - 后果：请求方等不到“已让出”就开始抢接口，容易撞上 “Unable to claim interface”。
  - 修复：后台路径上的这些等待换成 waitMs()，或者请求方按“收到 releasing 就继续等到 released”的方式延长上限。
  - 把握度：中（根据代码推断，没在浏览器里实测）。

    那条路径是先全部擦完再写，没有这个问题。按现在 HPM 的 4 KB 扇区不会触发，建议改成和 ARM 一样的顺序。

  中危

  11. 串口遇到可恢复的错误，页面也当成“断开”处理
  - 位置：app/serial/session.js:64-82 _readLoop()。
  - 原因：Web Serial 规定，帧错误、奇偶校验错、BufferOverrunError 这类错误不会关掉串口。port.readable 会换成一个新的流，读循环应该接着读。这里内层只有 finally，没有 catch，所以异常直接跳出外层 while，并发出
    close {unexpected:true}。
  - 后果：
    - 界面显示“串口已断开（设备被拔掉或占用）”，接收就此停止。
    - 实际上串口在系统层面还开着（isOpen 仍是 true，也没调过 port.close()），状态前后不一致。
    - 触发它很容易：波特率选错、线上有干扰、高速时 4 KB 的 bufferSize 溢出（页面在后台时更容易）。三个页面共用这个会话，所以串口助手、终端、RTT 转发会一起“断”。
  - 修复：按 Web Serial 的标准写法，内层加 catch：非致命错误发一个 error 提示后继续外层循环，只有 port.readable 变成 null 才算真断开。bufferSize 建议调大（比如 64 KB）。
  - 把握度：中高。这是对照 Web Serial 规范的标准读循环写法读码得出的，我没在真串口上制造帧错误验证。

  12. 调试器的“后台轮询忙就跳过”在操作排队时会失效
  - 位置：app/dbg/session.js:111-123 exclusive()。
  - 原因：_opBusy 是一个布尔量。两个操作排队时，第一个结束会把它清成 false，可第二个还在跑。
  - 复现（dbg-lock.mjs）：
  b 运行中，_opBusy = false
  后台轮询结果：没跳过，排队等到 b 跑完才执行
  - 后果：执行“单步跳出”这类长操作时，观察循环的读寄存器、RTT 泵、实时监视不再跳过，而是排队。目前只会多排一拍、晚一点刷新，不会读错。但这和注释里“绝不排队堆积”的约束不一致，以后改代码的人可能会依赖那个约束。
  - 修复：_opBusy 改成计数（进入时 ++，finally 里 --），或者判断 this._opChain 是否已经 settle。

  13. RTT 转发页和串口助手共用一个会话，事件也会互相触发

  - 后果：

    - 一个串口 open 会同时弹出两条提示。
  - 修复：open 事件里带上是哪个页面发起的，各页只处理自己发起的那一次；自动记录只由发起方启动。

    不管成没成功都返回 lastStepMode，调用方分不出这一步失败了。建议比较器不够时直接报错，不要去运行。
  - 工程生成页的 Node 版本输入框没有校验（gen/view.js:215 → bridge-kit.js:89,201）。输入内容原样拼进 .bat 和 .ps1，里面带 "、&、' 就会改变脚本逻辑。目前只有用户自己能填，算自伤；建议限制成 ^\d+\.\d+$。

    ，只能防传输损坏，防不了镜像被篡改。建议找不到行时至少给提示，或者把已知版本的哈希内置到脚本里。

    传输本身可靠，所以基本不会发生；真发生时，报错应该说清是“流错位”，而不是一串“应答超时”。

  高危

  14. J-Scope 和 SPI 的数据端点读循环：STALL 时空转，出错后不恢复
  - 位置：app/scope/transport.js:126-142 的 _worker()，app/spi/transport.js:117-133 的 _readWorker()，两处写法一样。
  - 复现（scope-stall.mjs，用假设备模拟）：
  stall: 100 ms 内 transferIn 调了 72164 次，errors=72162，running=true，存活 worker=2
  error: 100 ms 内 transferIn 调了 2 次，errors=2，running=true，存活 worker=0
  - STALL 的情况：transferIn 返回 status:'stall' 时只给错误计数加一，不调用 clearHalt，马上又读一次。端点会一直保持 STALL，于是循环空转，CPU 占满，数据也再收不到。
  - 出错的情况：transferIn 抛异常（USB 抖动、探针复位）时 worker 直接 break，没人重启。两个 worker 都退出后，数据面就停了。
  - 共同后果：running 仍是 true，页面还显示“采样中”。scope/view.js 里只有“1.5 s 没等到 DEF 包”这一种兜底，没有“数据流中断”的看门狗。
  - 修复：
    - STALL 时先 clearHalt('in', ep) 再重试，连续失败 N 次就整体停下并报错；
    - 读出错时上报给 view，由 view 停止采集并提示；
    - view 加一个看门狗：超过 1~2 s 没收到新的数据包就报“数据流中断”。
  - 把握度：高。

  中危

  15. 串口助手的 HEX 发送，单个数字的字节会和后一个拼成一个字节
  - 位置：app/core/hex.js:11-27 的 parseHex()。串口助手和 RTT 下行发送都用它。
  - 复现（hex-parse.mjs）：
  "0x1,0x2"        → 0x12          （用户的意思是两个字节 01 02）
  "1 2"            → 0x12
  "A 5 F 0"        → 0xa5 0xf0
  "0x01 0x2 0x03"  → 报“位数是奇数”
  - 后果：用户已经写了 0x 前缀或分隔符，明确表示这是单独的字节，结果被悄悄发成别的数据。
  - 修复：只有在没有任何分隔符的连续串里（比如 0103）才两位一组拆。凡是用空格、逗号或 0x 隔开的 token，每个就是一个字节，1 当作 01。

  16. SPI Flash 的“写数据”框会悄悄吞掉非法字符
  - 位置：app/spi/session.js:431 的 parseHexBytes()。注释写的是“非法字符直接报错，别静默吞”，但代码会把非十六进制字符直接删掉。
  - 复现（spi-hex-parse.mjs）：
  "zz 01"   → 0x01
  "0x1,0x2" → 0x12
  - 更麻烦的一点：如果框里全是非法字符，清理后就成了空串。bus-view.js:1065 遇到空数据会改用“256 B 递增图案”，于是这串图案被写进了 Flash。前提是已经勾了“我确认要擦写”。
  - 修复：遇到非法字符就报错；只有用户真的什么都没填，才用默认图案。

  低危

    partial.reset()。
  - J-Scope 每次停止后，没在 800 ms 内返回的 transferIn 还挂着。下次开始时它会被当成新一轮的 worker 继续跑，在飞的读请求会越积越多。目前不会读错数据，但 worker 数量不受控。
