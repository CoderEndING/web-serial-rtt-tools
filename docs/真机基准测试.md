# 真机场景基准（2026-10，STM32F103ZE + akaLinkPro）

用户点名的四步验收：**① 烧狂发固件 → 测 RTT Viewer / RTT 转发速率；② 烧 scope 固件 → 测 J-Scope
1 个变量 / 3 个变量的采样率；③ ①②重复 3 遍；④ 狂发 ↔ scope 交替烧录 5 遍并计时。**

一条命令复现：

```powershell
make open                                   # 8899 静态服务 + 9333 CDP 浏览器
make hw-campaign                            # 3 轮全场景 + 交替 5 遍（约 4 分钟）
make hw-campaign ARGS="--cycles=1 --alt=1"  # 冒烟一遍
```

脚本：`tools/selftest/hw-campaign.mjs`（+ `com-read.py` 当 RTT 转发的主机侧读者）。
原始数据落在 `tmp/campaign-result.json`。

- 狂发固件 = `tools/target-firmware/stm32f103_rtt_speed/build/fw.elf`（`while(1)` 猛发 `hello world!`）
- scope 固件 = `tools/target-firmware/stm32f103_scope/build/fw.elf`（19 个可采样变量）

## 1) 烧狂发固件 → 两个 RTT 通路的速率

每轮烧完狂发固件后先测 RTT Viewer（WebUSB 直读目标 RAM 的 RTT 环），断开后再测 RTT 转发
（探针侧 SWD 引擎把 RTT 搬进 CDC；主机必须真把 COM 口的数据读走，否则会背压 —— 这就是
`com-read.py` 存在的理由）。

| 轮次 | RTT Viewer | 轮询 | RTT 转发（主机读） | RTT 转发（探针侧搬运） | 收到的内容 |
|---|---|---|---|---|---|
| 1 | 235.5 KB/s | 105.8 Hz | 384.0 KB/s | 464.1 KB/s | `hello world!` 连续流 |
| 2 | 247.8 KB/s | 112.2 Hz | 383.8 KB/s | 464.6 KB/s | 同上 |
| 3 | 247.2 KB/s | 112.0 Hz | 383.8 KB/s | 464.1 KB/s | 同上 |

- 两条路的控制块都定位在 `0x2000000c`、`up × 2`，与 ELF 的 `_SEGGER_RTT` 一致。
- 转发的探针状态：`档位 45 MHz · 已搬运 3782 KB（9131 次）· 轮询 9132 · 读错 0 / RdOff 错 0 ·
  给 DAP 让路 31928 次` —— 转发引擎稳定，没有被 DAP/主机动作打断。
- 转发比 WebUSB 直读快，符合预期：转发是**探针自己**按自己的节奏搬（45 MHz SWD），
  主机只是排空 CDC；WebUSB 直读要来回走 1400 次/秒的命令往返。
- 两路**不能同时测**：RTT 环只有一个，谁快谁把数据拿走（页面自己的提示也写了这一条）。

## 2) 烧 scope 固件 → J-Scope 采样率

每次采样 3 s（目标侧真实时间，到点自动停），周期取 2 µs（冲上限）与 20 µs（50 kHz 目标）：

| 配置 | 读计划 | 名义 | 模型估算 | 实测 | 丢样本 |
|---|---|---|---|---|---|
| 1 变量 @2 µs | 1 span / 4 B（`g_lfsr`） | 500 kHz | 6.74 µs → 148 kHz | **396.8 / 398.8 / 398.7 kHz** | 探针 0 / USB 0 / 缺口 7 |
| 1 变量 @20 µs | 1 span / 4 B | 50 kHz | 同上 | **50.00 kHz**（三轮） | 探针 0 / USB 0 / 缺口 6 |
| 3 变量 @2 µs | 1 span / 10 B（`g_lfsr, g_far_cnt, g_far_sq100` 相邻，合并成一个 span） | 500 kHz | 8.44 µs → 118 kHz | **94.3 / 94.2 / 94.2 kHz** | 探针 0 / USB 0 / 缺口 6 |
| 3 变量 @20 µs | 1 span / 10 B | 50 kHz | 同上 | **50.00 / 50.00 / 49.44 kHz** | 探针 0 / USB 0 / 缺口 6~7 |
| 3 变量·地址分散 @2 µs | 3 span / 10 B（`g_lfsr, g_pair_b, g_tick`） | 500 kHz | 19.64 µs → 50.9 kHz | **60.3 / 60.0 / 60.3 kHz** | 探针 0 / USB 0 / 缺口 6 |

读法：

- **实测普遍优于模型估算**：模型按"3 次传输"保守估，固件里单字 span 走的是流水快路径
  （1 变量：实测 2.51 µs/样本 vs 模型 6.74；3 变量分散：实测 16.6 µs vs 模型 19.64）。
- **1 变量的 397 kHz 大概率卡在 0x83 的线速天花板**（≈1.75 MB/s ÷ 4 B/帧 ≈ 437 kHz），
  不是探针读不过来 —— 想再快得加宽帧（多采几个相邻变量反而"单位字节更划算"）。
- **3 变量相邻 vs 分散差 1.6 倍**（94 kHz vs 60 kHz）：同一结构体的成员会被合并成一个 span，
  一次块读全拿走；地址分散就得三次读。选变量时"勾同一片区域"是真能提速的。
- **三个配置在 50 kHz 目标下都是 0 丢样本**（探针跳拍 0、USB 排空不及 0）；
  每轮恒定出现的"缺口 6~7"与样本量无关（120 万样本和 15 万样本都是 6~7 个），
  说明是起跑/收尾的包边界记账，不是随机丢数据。

## 3) ④ 狂发 ↔ scope 交替烧录 5 遍（16 次烧录全记时）

| 遍 | 狂发烧录 | scope 烧录 |
|---|---|---|
| 1 | 741 ms | 1042 ms |
| 2 | 716 ms | 1042 ms |
| 3 | 728 ms | 1038 ms |
| 4 | 718 ms | 1040 ms |
| 5 | 716 ms | 1044 ms |
| 平均 | **0.72 s** | **1.04 s** |

页内「耗时小结」逐段（典型值）：探针 ~60 ms · 加载算法 ~240 ms · 读 DEV_ID 1~2 ms ·
擦除 62~68 ms（狂发）/ 124~139 ms（scope）· 写入 96~106 ms / 297~315 ms · 校验 21~23 ms / 89~91 ms ·
复位 104~124 ms。**16 次全部 ✅**（校验通过 + 复位后 PC 落在刚烧进去的固件里），零失败、零页面 JS 错误。

## 附：这次顺带验证到的

- 首轮烧录前的**跨页签协调**不再白等（日志是"没有其他页签在用探针"，~90 ms），
  幽灵页签与后台节流的修复见 `app/core/pace.js` 与 `app/core/probe-bus.js` 的注释。
- 每轮烧录之后 RTT / J-Scope / 转发都能立刻重新拿到探针（HID 与 0x83 数据端点各连各的），
  没有出现"烧完必须刷新页面才能用"的老毛病。
